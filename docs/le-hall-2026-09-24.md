# Le Hall — l'espace commun entre organisations volontaires

_Vision cliente, chantier 4 (24 septembre 2026). Ce document est la référence
de ce qui touche à l'**isolation entre organisations** : ce que le Hall
ouvre, ce qu'il n'ouvre pas, où les verrous sont, et comment on le prouve._

## 1. Pourquoi

Syraagensy l'a dit sans détour : « on s'y sent seul, coupé d'internet et des
autres ». Le poste est étanche par construction — c'est sa force —, mais
l'étanchéité ne doit pas être une solitude. Le Hall est un espace commun
que chaque organisation rejoint **par un geste explicite**, quitte d'un
geste, et dans lequel n'entre que ce qu'elle a choisi d'y montrer.

## 2. La règle

> Aucune donnée d'une organisation n'est jamais visible par une autre sans
> consentement explicite.

Le consentement est une ligne dans `hall_participation` (`org_id`,
`display_name`, `joined_at`, `joined_by_email`, `left_at`). Il n'existe que
si un **propriétaire ou un admin** l'a posé (`PUT /v1/hall/participation`,
`roles: ['owner','admin']`) ; il est retiré en posant `left_at`. Tout le
reste en découle.

## 3. Ce qui sort, ce qui ne sort jamais

| Sort vers les autres organisations | Ne sort jamais |
|---|---|
| Le nom d'affichage choisi (`display_name`, 60 car.) | L'adresse de qui que ce soit |
| La signature choisie par message (30 car., libre) | L'identifiant d'organisation ou de compte |
| Le texte du message (600 car.) et son heure | Le nom légal, si le nom d'affichage en diffère |
| Le nombre d'organisations qui participent | Quoi que ce soit des collections (tâches, clients, factures, fichiers…) |

La vue d'un message pour une autre organisation est **une fonction et une
seule** (`vue()` dans `amn-api/src/routes/hall.js`) : `{ id, org, signature,
body, createdAt, mienne }`. Le test `hall.test.js` vérifie que les clés du
message sont exactement celles-là.

## 4. Les verrous, dans l'ordre où ils s'appliquent

1. **La session.** `tenantAuth({ allowSupport: false })` sur toutes les
   routes : une **session de support** (un opérateur d'AMN DevSec posé sur
   une cliente) ne lit pas le Hall au nom de la cliente, n'y écrit pas, ne
   consent pas pour elle — 403. Le desktop l'exclut aussi du contexte de
   support (`NOT_IN_SUPPORT` dans `check-modules.mjs`).
2. **Le consentement.** Sans participation active : `GET /messages` et
   `POST /messages` → 403 `hall_non_rejoint`. La lecture joint sur
   `left_at IS NULL` : les messages d'une organisation partie cessent
   d'exister pour les autres **à l'instant**, sans état à nettoyer ; ils
   reviennent si elle revient.
3. **Les rôles.** Consentir : owner/admin. Écrire : owner/admin/member —
   jamais `guest` (403). Lire : tout membre d'une organisation qui participe.
4. **Les bornes.** 600 caractères par message, 30 de signature, 60 de nom
   d'affichage ; caractères de contrôle retirés ; vide refusé ; 10 passages
   par personne par dix minutes (`rateLimit` — les refus comptent, c'est un
   frein d'inondation) ; 20 signalements par heure.
5. **Le texte.** Stocké tel quel, rendu comme **texte** côté poste (React
   échappe ; aucun `dangerouslySetInnerHTML`, aucun lien interprété, aucune
   image). Vérifié en navigateur : `<img onerror>` et `<b>` apparaissent
   comme des caractères, aucun nœud `img`/`b` dans le DOM.
6. **La diffusion en direct.** Chaque organisation qui participe reçoit la
   trame `hall:message` **sur sa propre socket** (`hub.broadcast(…, orgId)`
   par participante), jamais un envoi à tous — le `broadcast` sans `orgId`
   est refusé bruyamment par le hub depuis la migration multi-tenant.
7. **La modération.** AMN DevSec voit tout (`GET /v1/admin/hall/messages`,
   masqués compris, avec le vrai nom de l'organisation), masque
   (`PUT /v1/admin/hall/messages/:id/masquer`, la ligne garde qui, quand,
   pourquoi — rien n'est supprimé) ; un message masqué disparaît pour tout le
   monde, autrice comprise, et la trame `hall:masque` le retire des écrans
   ouverts. « Signaler » crée une demande d'assistance « Signalement dans le
   Hall » — un humain tranche.
8. **Aucune copie locale.** Le Hall ne passe pas par `shared_records` ni par
   la file hors ligne, exprès : ce sont des messages d'autres organisations,
   et le poste ne doit pas en garder une copie qui survivrait au retrait du
   consentement. Sans lien, l'écran le dit et attend.

## 5. La preuve

`amn-api/test/hall.test.js` — 7 tests, dans la suite complète (473/473) :

- sans consentement : 403 en lecture et en écriture ; une membre ne consent
  pas (403) ; le propriétaire consent, le retire, la porte se ferme à
  l'instant ;
- la vue d'un message a exactement six clés ; le corps de réponse ne
  contient ni adresse, ni `org_id`, ni le nom légal quand un nom d'affichage
  a été choisi ;
- quitter efface pour les autres ; revenir rend ;
- une session de support : 403 sur les trois routes ;
- un invité lit, n'écrit pas ;
- XSS stocké tel quel, 601 caractères refusés, vide refusé, caractères de
  contrôle retirés, signature bornée, 11ᵉ passage freiné (429) ;
- signaler crée la demande d'assistance visible dans la file d'AMN ; masquer
  efface pour tout le monde ; une cliente ne touche pas à l'administration.

Côté poste, `scratchpad/chantier4.mjs` a joué le parcours entre Syraagensy
et Plomberie Marchetti (voir le rapport de vision, §2.3).

## 6. Ce qui reste (à dire, pas à cacher)

- Pas d'écran de modération dans la Tour : la modération passe par l'API
  d'administration (documentée ci-dessus) et par la file d'assistance. Brief
  Claude Design dans le rapport (§5).
- Pas de fils ni de réponses : une seule conversation, cent derniers
  messages. C'est voulu pour la première version — un Hall, pas un forum.
- Pas de notification de nouveau message hors de l'écran du Hall : le choix
  est de ne pas interrompre pour ce qui n'est pas le travail.
