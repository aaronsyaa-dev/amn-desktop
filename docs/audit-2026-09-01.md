# Audit du 1er septembre — avant de construire

*Bloc 0 du brief « comptes, bienvenue, sécurité ». Quatre questions, quatre
réponses lues dans le code réel des deux dépôts — pas supposées.*

## 1. Les éditions sur web et mobile

**Comment le web sert les deux éditions aujourd'hui.** L'édition est décidée
À LA COMPILATION, jamais à l'exécution : `vite.edition.ts` résout les alias
`@edition/*` selon `AMN_EDITION`, et `scripts/build-web.mjs` produit UN bundle
par édition (`build:web` = interne « AMN Business », `build:web:business` =
cliente « AMN Desktop »). Le manifeste PWA et le titre d'onglet sont substitués
au build (`editionIdentityPlugin`). Côté serveur, `lib/links.js` connaît DEUX
adresses publiques : `APP_PUBLIC_URL` (interne) et `APP_BUSINESS_PUBLIC_URL`
(clientes), et choisit selon l'organisation du destinataire.

Il y a donc deux déploiements attendus. Le `vercel.json` du dépôt construit
l'édition INTERNE par défaut : le projet Vercel qui sert « AMN Desktop » doit
impérativement construire avec `AMN_EDITION=business`. C'est une configuration
de déploiement, invisible depuis le code — et la cause la plus probable du
symptôme remonté (« AMN Desktop affiche le centre de supervision ») : un
projet construit sans cette variable sert le bundle interne sous l'adresse des
clientes. À vérifier chez Vercel (action Aaron, listée au rapport).

**Ce que le code fait d'un mauvais couple compte/édition.** Le build interne
REFUSE une organisation cliente à la connexion (`AuthContext.adoptSession`) avec
« Utilisez l'application AMN Desktop » — sans lien, sans redirection. Le build
cliente accepte un compte AMN DevSec (Aaron vérifie ce que voit sa cliente).
Le Bloc 7 remplace le refus sec par une redirection vers la bonne adresse,
fournie par le serveur (`appUrl` dans l'identité d'organisation).

## 2. Le routage des notifications

Trois canaux, tous scopés par organisation :

- **WebSocket** (`ws/hub.js`) : `broadcast(message, orgId)` n'itère que les
  sockets dont `__orgId` — résolu depuis le JETON, jamais déclaré par le client —
  vaut l'organisation visée ; un appel sans `orgId` est abandonné bruyamment.
  Une session de support ouvre une socket sur l'organisation de la CLIENTE.
- **Web Push** (`lib/push.js`) : `pushToUser(db, orgId, email)` ne lit que les
  abonnements de `(org_id, user_email)`.
- **Notifications de bureau** (`NotificationsManager.tsx`) : réagissent au
  flux de la socket de leur propre organisation ; les notifications de parc
  (« Espace client ouvert ») viennent du relevé ADMIN, réservé à l'opérateur.

Le prestataire reçoit donc les siens (socket AMN DevSec) et ceux de ses
clientes (relevé de parc, et socket de support quand il est dans un dossier).
Aucun chemin ne diffuse à « tout le monde ». Le Bloc 6 le PROUVE par test.

## 3. La capacité email

**Aucune.** Ni nodemailer, ni SendGrid, ni SMTP dans amn-api — c'est écrit dans
le code des invitations : « amn-api has no mail transport and inventing one
here would be worse ». Toute remise (invitation, mot de passe temporaire, lien
d'appel) est un lien ou un secret affiché UNE fois, à transmettre soi-même.

Conséquence pour le Bloc 3 : pas de lien de réinitialisation par email —
le bouton « Mot de passe oublié » crée une DEMANDE visible côté Tour de
contrôle et le dit honnêtement à la personne. Rien de faux n'est envoyé.

## 4. La gestion de comptes existante

Côté serveur, tout existe déjà :

| Geste | Route |
| --- | --- |
| lister les membres | `GET /v1/auth/users` (tout membre) |
| inviter (email + rôle) | `POST /v1/auth/invitations` (owner/admin) |
| accepter, choisir son mot de passe | `POST /v1/auth/invitations/accept` (public) |
| changer un rôle | `PUT /v1/auth/users/:id/role` (owner/admin, dernier propriétaire protégé) |
| suspendre / réactiver | `PUT /v1/auth/users/:id/status` |
| ouvrir un compte chez une cliente | `POST /v1/admin/organizations/:id/users` |
| réémettre un accès | `POST /v1/admin/organizations/:id/invitations` |
| mot de passe temporaire | `POST /v1/admin/organizations/:id/users/:userId/temp-password` |
| supprimer un compte | `DELETE /v1/admin/organizations/:id/users/:userId` |

Côté desktop : `MembersSection` (Réglages, deux éditions, masquée en session
de support) sait lister, inviter, changer un rôle, suspendre. Le dossier
d'organisation de la Tour de contrôle sait ouvrir un compte, réémettre,
remettre un mot de passe, retirer. Ce qu'Aaron a vu (« supprimer » et « mot
de passe ») est le dossier ; la section Membres vit en bas des Réglages, sans
écran à elle.

**Ce qui manque réellement** : un écran Membres à part entière, la notion de
PLACES (aucune colonne `seats` — l'atelier choisit un nombre de sièges qui ne
sert qu'à déduire la formule), et un mécanisme pour demander une place de
plus. Les demandes de module existent (`module_requests`, lues par un humain
dans la Tour) et servent de modèle.

## Ce que l'audit change au plan

- Bloc 1 : `seats` devient une colonne d'organisation, imposée par le serveur
  à l'invitation ; la demande de place rejoint une file de demandes commune.
- Bloc 3 : chemin « prestataire prévenu » uniquement.
- Bloc 4 : la file de demandes est UNE table (`support_requests`) à plusieurs
  natures — message, place, mot de passe oublié — et une seule vue Tour.
- Bloc 7 : redirection par `appUrl` serveur + consigne Vercel.
